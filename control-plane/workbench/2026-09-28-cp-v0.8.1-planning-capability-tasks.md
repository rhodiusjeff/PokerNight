## 1. Scope

Deliver file-backed planning and work-item creation across bounded horizons, ad hoc conversations,
and execution discovery. Capture precedes tracked processing. All proposed operational changes
use the same exact-subject review/decision and protected admission contract. Provide guided
interaction through Codegen or Planning and Design, with narrowly scoped specialist support.

In scope: planning context and lifecycle; source/asset capture; deferred items; repeatable shared
skills; proposed Canon/specifications/DAG; finding tracking; review and approval/waiver; admission
and merge validation; affected execution-consumer compatibility; distribution and isolated trials.

Out of scope: Dolt or another shared service, beads integration, automatic claiming, ticket-system
connectors/synchronization, autonomous conflict resolution, automatic production deployment,
Poker Night product implementation, repository blanking, and execution redesign in this stage.
Execution redesign is intended follow-on work after planning and Canon/work admission, not a
permanent exclusion. Current execution changes are limited to compatibility required by this stage.
Read external ticket references without implying a connector. Use the
existing diagram provider/checkpoint mechanism; no new drawing provider or background sync engine.

Timing-log consolidation/redesign is deferred by Operator direction. Preserve the current session
files, event schema, append behavior, retention policy, and historical records; do not implement
the suggested unified JSONL stream or change Git tracking. CPv1 will collect timing telemetry in
an OpenTelemetry (OTel) sink; sink implementation and migration are outside V0.8.1. Necessary
command/context compatibility must preserve current timing semantics. Visible test progress below
remains required and must not become a timing-storage overhaul.

Required architecture intent: one repository-owned operational Canon/specification/DAG revision;
execution progress separate; one MR per admission; no historical evidence rewritten. No new
documents directly under the control-plane root: ad hoc/discovery under `control-plane/ad-hoc/`,
deferred records under `control-plane/deferred/`; operational placement still requires G-01.

Control-plane runtime state belongs under `control-plane/state/`, which already contains instance
state, installation metadata, and timing. Keep local bindings gitignored and worktree-local there.
Exact state layouts and consumer changes remain G-01 work; do not indiscriminately move historical
packet evidence or treat source/proposal documents as runtime state. Execution status remains
outside the operational specification revision, even when stored under the same control-plane root.

## 5. Scope And Verification Rules

- This task order is advisory dependency sequencing, not an approved phase DAG or linearized tracker.
  Independent capture/lifecycle and skill work may proceed in parallel only after shared contracts
  are fixed. Admission depends on their outputs; forge enforcement depends on the validator contract.
- Keep required execution-consumer repairs in this stage; execution redesign follows after planning
  and Canon/work admission. Do not silently fold later execution redesign into compatibility fixes.
- Use existing test suites and helpers where applicable. Add fixtures for behavioral gaps rather
  than new test infrastructure by default. Test ordinary non-admission changes as well as refusals.
- Preserve an exact subject for every assessment, decision and admission. Do not preserve only a
  digest when the underlying bytes would be lost. No required shadow copy of maintained proposals.
- Open planning findings remain warnings under the accepted policy; an incomplete implementation
  task or failed integrity test is not proof that the delivered capability works.
- No implementation task is checked at document creation. Discussion acceptance is not test
  execution. Record future evidence beside task IDs and maintain scope changes explicitly.

### Fast Checks And Observable Stress Trials

The Operator requires short routine verification and visible progress during the longer work of
stressing agents, commands, personas, and skills. Reuse V0.8 test fixtures, assertions, temporary
remotes/clones, provider mocks, and timing repairs; adapt tests whose expected behavior is knowingly
superseded. Do not build a new test framework merely to rename existing coverage.

- Run the cheapest relevant deterministic checks after each meaningful change; run broader
  regression at coherent integration checkpoints, not after every prompt edit. Measure the baseline
  before promising durations. Initial recommended targets, subject to measurement: scoped checks
  around two minutes or less and a normal blocking batch below ten minutes. These are tuning targets,
  not permission to omit required checks or claims of current measured performance.
- Start agent evaluation with a small selected stress set, covering both primary agents and
  relevant specialist handoffs, then expand only for uncovered risks or observed failures. Avoid
  a full cross-product of every agent, command and scenario. Use bounded scenario turns, elapsed
  time, and retries; record a timeout/stall as such rather than rerunning until green.
- Stress authorization ambiguity, explicit confirmation versus deferral, scope creep, missing
  capture/binding, conflicting sources, stale review/base, interrupted transfer/admission, and
  partial provider failure. Evaluate actual tool actions, artifacts, and retained provenance as
  well as the Operator-facing conversation. A mock provider or deterministic persona fixture is
  not evidence of real agent behavior; classify each run honestly.
- Keep source-only Poker Night trials separate from fast blocking checks. Execute them in visible
  stages with checkpoints and known coverage; repeated corpus processing needs a stated changed
  subject or new test objective. Do not silently turn one trial into an unbounded exploration.
- Before a batch, show its goal, selected scenario IDs, expected budget/limits, and log location.
  Emit incrementally flushed records on batch/scenario start, meaningful milestones, waits,
  failures, timeout, interruption, and finish. Each records run/scenario identity, relevant use
  cases, harness/model/persona where applicable, timestamps/elapsed time, outcome and evidence links.
- Show completed/total scenarios, passed/failed/blocked/skipped/remaining counts, current action,
  last meaningful progress and next step. Distinguish awaiting Operator input, provider/tool wait,
  and actual test work. Report skips and limitations, never silently count them as passes.
- During long runs, provide a lightweight liveness update at a documented cadence (recommended
  30 seconds) and substantive milestones in chat. A heartbeat is not proof of progress. Where a
  harness cannot expose live internals, disclose that limitation, show elapsed time/last output,
  and enforce the scenario deadline rather than claim unseen activity or poll indefinitely.
- Keep redacted incremental logs and resume summaries under a designated validation-run subfolder
  of `control-plane/state/`; exact name and Git retention policy must be selected under G-01.
  Link test evidence to tasks without treating observed run status as operational authority. Log
  actions/results, not private chain-of-thought, credentials, or sensitive source payloads.
- End every batch with results, coverage, failures/limitations, duration and the exact next action.
  On interruption, retain completed results and a resume point rather than restart invisibly.
  Explain budget overruns and ask before widening authorized test scope or expenditure.
